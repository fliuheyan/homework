# Data Cleaning Solution

---

## 1. Objectives and Design Principles

This project builds a repeatable ETL workflow around an Excel file containing three sheets: `orders`, `customer`, and `survey`. It also includes a data quality reporting layer and Grafana-based monitoring.

The design principles are as follows:

1. **Raw data must remain traceable**: the raw layer preserves the displayed Excel values as ingested, without applying business cleaning during loading.
2. **Cleaning logic must be rerunnable**: the core layer is produced by a transformer plugin chain, so cleaning can be rerun without re-ingesting the source file.
3. **Data quality issues must be measurable**: `etl/data_check.py` outputs a Markdown report and writes quality statistics into PostgreSQL.
4. **Runtime status must be observable**: the `audit` tables and views expose batch status, quality metrics, table freshness, and row counts to Grafana.

---

## 2. Layered Architecture

```
Excel / CSV
    │
    ▼
raw layer       Raw landing zone that preserves displayed cell text + batch audit fields
    │
    ├── data_check.py      Generates the Data Quality Report and writes quality stats to audit tables
    │
    ▼
core layer      Uses transformers to standardize, link, and drop records that cannot enter core
    │
    ▼
audit layer     Stores ETL run logs and quality summaries, and provides Grafana query views
```

### 2.1 Raw Layer

| Table | Description |
|---|---|
| `raw.orders` | Raw order data, with column names ending in `_text` |
| `raw.customer` | Raw customer data, with column names ending in `_text` |
| `raw.survey` | Raw survey data, with column names ending in `_text` |

Each raw table includes the following audit fields:

| Column | Description |
|---|---|
| `source_file` | Source file name |
| `sheet_name` | Source sheet name |
| `load_time` | Load time |
| `batch_id` | Ingestion batch ID |
| `row_num_in_sheet` | Original row number in Excel |
| `ingested_at` | Database write timestamp |

### 2.2 Core Layer

| Table | Description |
|---|---|
| `core.customer` | Standardized customer master data |
| `core.orders` | Standardized order data linked by the `customer_id` foreign key |
| `core.survey` | Standardized survey data that can link to `customer_id` or `order_id` |

### 2.3 Audit Layer

| Table/View | Description |
|---|---|
| `audit.etl_run_log` | Start time, end time, status, row counts, and error message for each ETL batch |
| `audit.data_quality_issue_summary` | Field-level quality issue statistics |
| `audit.data_quality_table_summary` | Table-level totals and invalid-record counts |
| `audit.v_etl_run_metrics` | Per-run duration and status metrics |
| `audit.v_etl_health_kpis` | Latest status, success rate, average runtime, and P95 runtime |
| `audit.v_data_quality_batch_metrics` | Per-table issue rate for each batch |
| `audit.v_data_quality_issue_metrics` | Time series of field-level quality issues |
| `audit.v_latest_data_quality_summary` | Latest batch quality snapshot |
| `audit.v_table_volume` | Current row counts in raw/core tables |
| `audit.v_table_freshness` | Latest timestamps and freshness lag for raw/core tables |

## 3. Raw Ingestion Design

The job of `etl/ingest_raw.py` is to write Excel cell content into the raw layer as close as possible to the displayed value, instead of normalizing it in advance.

### 3.1 Ingestion Characteristics

1. It uses `openpyxl` to read cell values and `number_format`.
2. It preserves Excel display formats whenever possible, for example:
   - Chinese-style dates written with year/month/day characters, such as `2021-08-08` in a localized display format
   - Localized short dates: `2/ Aug/`
   - Currency suffixes: `43.58 €`
3. It skips rows that are completely empty.
4. It generates a shared `batch_id` for each import run.

### 3.2 Why the Raw Layer Does Not Clean Data

- It makes source-data issues traceable.
- It avoids hiding formatting problems during ingestion.
- It allows the cleaning pipeline to be rerun later without re-importing the source file.

## 4. Data Quality Report Design

The data quality report is generated by `etl/data_check.py`, with the default output path `/app/reports/data_quality_report.md`. By default, it checks only the latest `batch_id` and also writes statistics into `audit.data_quality_issue_summary` and `audit.data_quality_table_summary`.

### 4.1 Report Structure

The report contains two sections:

1. **Summary by Table**
   - `table`
   - `total_records`
   - `total_issues` (counted as distinct rows with at least one issue)
2. **Field-level issue details for each table**
   - `column`
   - `description`
   - `invalid_count`

### 4.2 Null Definition

The following values are treated as null consistently:

`""`, `null`, `none`, `nan`, `na`, `n/a`, `-`

These values are usually not counted as format errors, but they are counted as issues when a rule requires a non-null value.

### 4.3 Validation Rules by Table

#### `raw.orders`

| Column | Check | Rule |
|---|---|---|
| `order_date_text` | Order date format | Must be a parsable year-first date, and the original format must match `YYYY/M/D` or `YYYY-MM-DD` |
| `net_amount_text` | Amount format | Must be a plain numeric value without currency symbols; decimals are allowed, but `€/$/£/¥/₩` are not |

#### `raw.customer`

| Column | Check | Rule |
|---|---|---|
| `birthday_text` | Birthday format | Must be a valid `YYYY-MM-DD` date |
| `gender_text` | Gender value | Only `male` / `female` are accepted |
| `country_text` | Country value | Only `DE` is accepted |
| `zip_code_text` | ZIP code format | Must be 4 to 5 digits and cannot be empty |
| `city_text` | City format | Cannot be empty and must not include a ZIP code |

#### `raw.survey`

| Column | Check | Rule |
|---|---|---|
| `respondent_key_text` | Reference key format | Must be a valid email or `ORD` followed by digits |
| `respondent_key_text` | Customer uniqueness | If it is an email, the normalized value must not match multiple customers in raw customer data |
| `diet_pref_text` | Non-null check | Cannot be NULL or an empty string |

## 5. Cleaning and Core Load Design

`etl/main.py` first reads the raw data from the latest batch, then discovers and executes plugins under `etl/transformers/<table>/`, and finally rebuilds the core layer.

### 5.1 `raw.orders` → `core.orders`

#### Known Issues

| Column | Issue |
|---|---|
| `email_text` | Inconsistent letter case and surrounding whitespace |
| `order_date_text` | Mixed date formats, including Chinese text, English month names, and missing years |
| `net_amount_text` | May contain `€` or spaces |
| `order_number_text` | May not follow `ORD\d+` |

#### Transformer Chain

| Order | Plugin | Actual Processing |
|---|---|---|
| 1 | `01_normalize_email.py` | Applies `strip()`, stores the result in `email`, and generates lowercase `email_norm` |
| 2 | `02_normalize_order_date.py` | Parses Chinese dates; for values like `2/Aug/`, fills in the default year `2021`; writes the result to `order_date` |
| 3 | `03_normalize_net_amount.py` | Removes `€` and spaces, then converts to numeric |
| 4 | `04_normalize_order_number.py` | Applies `strip()` and validates against `^ORD\d+$`; invalid values are set to null |

#### Core Load Rules

- Join to `core.customer` through `email_norm`.
- Orders that cannot be linked to a customer are dropped.
- Orders with null `order_date`, `net_amount`, or `order_number` are dropped.
- If `order_number` is duplicated, only the first row is kept.
- `currency_code` uses the table default value `EUR`.

### 5.2 `raw.customer` → `core.customer`

#### Known Issues

| Column | Issue |
|---|---|
| `email_text` | Inconsistent letter case and surrounding whitespace |
| `birthday_text` | May contain Chinese-style dates or other parsable formats |
| `gender_text` | May use abbreviations such as `m/f` |
| `country_text` | May appear as `Deutschland`, `Germany`, or other variants |
| `city_text` / `zip_code_text` | City and ZIP code may be mixed together |
| `loyalty_score_text` | Stored as text and must be converted to numeric |

#### Transformer Chain

| Order | Plugin | Actual Processing |
|---|---|---|
| 1 | `01_normalize_email.py` | Generates `email` and `email_norm` |
| 2 | `02_normalize_birthday.py` | Parses the birthday and writes it to `birthday` |
| 3 | `03_normalize_gender.py` | Maps `m/male → male`, `f/female → female`, and converts other values to `unknown` |
| 4 | `04_normalize_country.py` | Maps `de/deutschland/germany → DE`; for other non-empty values, keeps the first two uppercase letters |
| 5 | `05_normalize_city_zip.py` | If `zip_code_text` is empty, attempts to extract a 4-5 digit ZIP code from `city_text`; also writes the numeric `loyalty_score` column |

#### Core Load Rules

- All customer records are written to `core.customer`.
- Duplicate `email_norm` values are allowed.
- `loyalty_score` is currently only converted to numeric and is **not restricted to the 1-3 business range in the current implementation** (see Section 8.2 below).

### 5.3 `raw.survey` → `core.survey`

#### Known Issues

| Column | Issue |
|---|---|
| `respondent_key_text` | May be an email, an order number, or an invalid value |
| `diet_pref_text` | May be empty and may contain German values |
| `taste_pref_text` | May be empty and may contain misspellings |

#### Transformer Chain

| Order | Plugin | Actual Processing |
|---|---|---|
| 1 | `01_normalize_key_type.py` | Identifies `email`, `order_number`, or `invalid`, and preserves `respondent_key` |
| 2 | `02_normalize_diet_pref.py` | Normalizes to lowercase and maps `vegetarisch` to `vegetarian` |
| 3 | `03_normalize_taste_pref.py` | Normalizes to lowercase and fixes `sweeet` to `sweet` |

#### Core Load Rules

- When `key_type = order_number`, link through `core.orders.order_id` using `order_number`.
- When `key_type = email`, link through `core.customer.customer_id` using `email_norm`.
- Only a **unique email** is allowed to populate `customer_id`; duplicate emails are not linked.
- Survey records that cannot be linked are still kept, but their foreign keys remain null.

## 6. End-to-End ETL Flow

```
Excel file
   │
   ▼
ingest_raw.py
   │   Read sheets -> write raw.* -> assign batch_id
   ▼
data_check.py
   │   Generate Markdown quality report
   │   Write back audit.data_quality_* summary tables
   ▼
main.py
   │   Read latest batch
   │   Discover and execute transformers
   │   TRUNCATE core.survey/core.orders/core.customer
   │   Rewrite core tables
   ▼
audit.etl_run_log
   │   Record success/failed status, row counts, and error messages
   ▼
Grafana
```

### 6.1 Characteristics of the Current Implementation

1. **The latest batch is the default scope**: both `main.py` and `data_check.py` operate on the latest `raw.orders.batch_id` by default.
2. **The core layer is rebuilt on each run**: every execution clears the core layer first and then writes the current results back.
3. **Audit logging is complete**: both successful and failed runs are recorded in `audit.etl_run_log`.

## 7. Grafana Monitoring Design

The current repository already includes Grafana provisioning files and queries PostgreSQL `audit` views directly.

### 7.1 Monitoring Topics Already Implemented

Based on the README and the SQL view design, the current dashboard mainly covers:

- Latest ETL status
- Job success rate
- Average runtime
- Latest batch quality issue count
- ETL runtime trend
- Quality issue trend
- Per-table freshness
- Raw/Core table volume

### 7.2 Metric Source Mapping

| Monitoring Topic | Data Source |
|---|---|
| Runtime status, success rate, average/P95 runtime | `audit.v_etl_health_kpis` |
| Per-run details | `audit.v_etl_run_metrics` |
| Batch-level issue rate | `audit.v_data_quality_batch_metrics` |
| Field-level quality trends | `audit.v_data_quality_issue_metrics` |
| Latest batch quality overview | `audit.v_latest_data_quality_summary` |
| Table volume | `audit.v_table_volume` |
| Table freshness | `audit.v_table_freshness` |

### 7.3 Design Value

This dashboard answers four core questions:

1. **Did the job finish successfully?**
2. **Is data continuing to enter the system batch by batch?**
3. **Has data quality declined in the latest batch?**
4. **Are data volume and freshness abnormal in the raw/core tables?**

## 8. Current Boundaries and Potential Improvements

To keep the documentation aligned with the implementation, the current solution still has the following boundaries:

1. **The data quality rules are stricter than the cleaning rules**
   - For example, `birthday_text` in data quality checks only accepts `YYYY-MM-DD`.
   - However, the cleaning stage still attempts to parse Chinese-style dates or other parsable formats.

2. **`loyalty_score` is only converted to numeric and does not enforce a business value range**
   - If the required range is `1-3`, an additional rule should be added in a transformer or before loading into core.

3. **Order numbers are not normalized to a consistent letter case**
   - The current logic only applies `strip()` and validates `^ORD\d+$`.
   - If source data may contain values such as `ord001`, explicit uppercase normalization can be added.

4. **Duplicate customer emails are allowed**
   - This creates a business tradeoff with the survey uniqueness strategy: raw customer records are preserved, but survey rows are linked only when the email is unique.

5. **The core layer uses full rebuilds**
   - This is suitable for assignment scenarios and small datasets.
   - In production, incremental merge logic, idempotent writes, and finer rollback strategies should be considered.

---

## 9. Summary

The core purpose of this solution is not to “fix dirty data once and for all,” but to establish an ETL pipeline that is **traceable, rerunnable, and observable**:

- The raw layer preserves the original input.
- The core layer stores reusable cleaning results.
- The audit layer provides runtime and quality monitoring.
- Grafana presents ETL health, data quality, and table freshness in one place.

This supports the current assignment requirements while still leaving room for future rule expansion, stronger monitoring, and a more production-ready design.
